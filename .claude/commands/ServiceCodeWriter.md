# /ServiceCodeWriter  [wave:{n}]  OR  [wave:{n} service:{name}]  OR  [{service-name}]

Write Terraform code for a service. **No terraform CLI is invoked** — this command
only generates files and runs lightweight in-process sanity checks. Validation
(terraform init/validate/fmt/plan/test) is a separate command: `/TerraformValidator`.

Modes:
  /ServiceCodeWriter                            → write next service in next unbuilt wave
  /ServiceCodeWriter wave:2                     → write next unwritten service in wave 2
  /ServiceCodeWriter wave:2 service:rds-users   → write one specific service in a wave
  /ServiceCodeWriter rds-users                  → write one specific service (wave auto-looked-up)

All generated files go into `terraform/`. Build log goes into `agent/execution.md`.

## Step 1 — Load state and validate

Read `.claude/memory/handoff.json` then `.claude/memory/tf-state.json`.

Show banner: `📂 {project}  |  {phase}  |  terraform/`

Check all three gates confirmed. If any wave has unconfirmed inputs that the build
needs, stop and show:
```
❌ Cannot write Wave {n} — inputs not yet confirmed.
   Run /BuildPlan wave:{n} first.
```

Read all confirmed input files:
- `.claude/memory/01-services.json`
- `.claude/memory/02-build-plan.json`
- `.claude/memory/03-inputs-wave-{n}.json` (for the target wave only)

Read `terraform/` references from the skill's terraform-standards.md.
Read `references/iam-roles-reference.md` for IAM patterns per service type.

**IAM check:**
Verify `iam_review: "CONFIRMED"` in `tf-state.json`. If not confirmed:
```
⚠️  IAM review not confirmed. It is recommended to run /IAMModelerConfirm before writing.
    Continue anyway? [yes / run /IAMModelerConfirm first]
```
If user says yes — proceed. If no — stop and let them run /IAMModelerConfirm.

## Step 2 — Determine what to write

Parse $ARGUMENTS:
- `wave:N service:name` → write specific service in specific wave
- `wave:N`             → write next unwritten service in wave N
- `{service-name}`     → look up wave from 02-build-plan.json, write that service
- (nothing)           → find next unwritten service across all waves

A service is considered "unwritten" if its status in `04-build-progress.json` is
absent, `PENDING`, or missing. Services at status `CODE_WRITTEN` or `COMPLETE`
are skipped (use `/TerraformValidator` for the next step, or re-run this command
with an explicit service name to overwrite).

**Dependency check before writing any service:**
All services from earlier waves must be `COMPLETE` in `04-build-progress.json`
(i.e. they must have passed validation, not just code generation). If not:
```
❌ Cannot write {service} (Wave {n}) — Wave {n-1} not complete:
   Missing: {service-name} (Wave {n-1})
   Finish Wave {n-1} first:
     /ServiceCodeWriter wave:{n-1}
     /TerraformValidator wave:{n-1}
```

Also check that inputs are confirmed for the wave being written:
```
❌ Cannot write Wave {n} — inputs not confirmed.
   Run: /BuildPlan wave:{n}
```

## Step 4 — Generate module files

Write ALL files to `terraform/modules/{service-name}/`. Do NOT print file contents to chat.

Files to generate (follow terraform-standards.md for all rules):
- `terraform/modules/{service-name}/main.tf`
- `terraform/modules/{service-name}/variables.tf`
- `terraform/modules/{service-name}/outputs.tf`
- `terraform/modules/{service-name}/versions.tf`      ← required_providers only, NO required_version
- `terraform/modules/{service-name}/tests/main.tftest.hcl`
- `terraform/modules/{service-name}/tests/fixtures/test.tfvars`

Key rules from standards:
- Use locals for all name construction
- Every resource gets `tags = local.common_tags`
- Tags: Project, Environment, ManagedBy="terraform", Module
- No hardcoded regions, account IDs, or ARN fragments
- Security rules: S3 public access block, SG restrictions, RDS deletion protection, secrets in SM

**IAM generation for this service (use pre-generated files):**

Read `agent/review/iam-model-review.json` — find all IAM entries for this service.

1. If this service is `iam-base-roles`:
   The file `terraform/modules/iam-base-roles/main.tf` was already generated by
   `iam-generator.py`. Do NOT regenerate it. It is ready to apply.
   Verify it exists. If missing: run `python3 agent/scripts/scaffold/iam-generator.py`.

2. If this service has a `terraform/modules/{service}/iam.tf` (pre-generated):
   Read it. The inline policies and resource-based policies are already there.
   Add any `extra_permissions` from `03-inputs-wave-{n}.json` IAM section to `iam.tf`.
   Apply any `permission_boundary_arn`, `iam_path`, `lambda_vpc_enabled` values
   from the wave inputs file to the `iam-base-roles` variables.tf.

3. Wire IAM outputs from iam-base-roles into this service module's `variables.tf`:
   - Add `var.{output_name}` for each role ARN this service needs

4. After wiring, update `build_status` for this service's IAM rows in
   `agent/review/iam-model-review.json` to `"built"`.

No IAM code is written from scratch here — only the pre-generated iam.tf is used and wired.

Show only: `Generated: terraform/modules/{service-name}/  (5 files + tests)`

## Step 4b — Apply IAM roles for this service (wave-scoped)

Read `agent/review/iam-model-review.json`. Find all entries where `module == "{service-name}"`.

**If no IAM role entries found for this service** (e.g. pure S3 bucket, SQS queue):
- Set `iam_status: "NOT_REQUIRED"` (used in Step 7).
- Skip to Step 5.

**If role entries exist**, run init and target-apply for each `aws_iam_role` and
`aws_iam_role_policy_attachment` resource listed in `terraform/modules/{service-name}/iam.tf`:

```bash
cd terraform/modules/{service-name}
terraform init -backend=false 2>&1
terraform apply \
  -target=aws_iam_role.{role_resource_name} \
  -target=aws_iam_role_policy_attachment.{attachment_resource_name} \
  -auto-approve 2>&1
```

Repeat for every role+attachment pair in `iam.tf`. Capture full output to `agent/execution.md`.

**On success (exit code 0):**
- Set `iam_status: "CREATED"` (Step 7).
- Update `build_status` to `"built"` for each applied role in `agent/review/iam-model-review.json`.
- Show: `✅ IAM roles applied  ({n} roles created for {service-name})`

**On IAM permission failure** — output contains any of:
`is not authorized to perform: iam:CreateRole`
`is not authorized to perform: iam:AttachRolePolicy`
`AccessDenied`
`UnauthorizedOperation`

- Set `iam_status: "SKIPPED"` (Step 7).
- Do NOT stop or fail the service build — continue to Step 5.
- Show this warning (and append to `agent/execution.md`):

```
⚠️  IAM role creation SKIPPED — Terraform executor lacks permission.
    Roles that must be created manually before deploying {service-name}:

      {for each role in iam.tf}
      Role:    {role_name}   (resource: aws_iam_role.{resource_name})
      Trust:   {trust_principal}
      Attach:  {managed_policy_arns — comma-separated}

    Options to unblock:
      A) Add iam:CreateRole + iam:AttachRolePolicy to your Terraform executor role,
         then re-run: /ServiceCodeWriter {service-name}
      B) Create the roles manually in AWS, then update iam_status to CREATED in
         .claude/memory/04-build-progress.json and re-run: /TerraformValidator {service-name}

    ⚠️  The service module code is valid — but deployment will fail until
        these roles exist in AWS.
```

**On any other terraform error** (non-permission failure):
- Set `iam_status: "ERROR"` (Step 7).
- Log full output to `agent/execution.md`.
- Show: `⚠️  IAM apply error (non-permission) — see agent/execution.md. Continuing with service build.`
- Continue to Step 5.

## Step 5 — Write per-service wiring file (NO shared-file edits)

Instead of editing shared `terraform/environments/{dev,prod}/main.tf`, write exactly
**one file per environment per service** containing only that service's `module { ... }` block:

- `terraform/environments/dev/modules/{service-name}.tf`
- `terraform/environments/prod/modules/{service-name}.tf`

Create the `modules/` subdirectory if it doesn't exist. Terraform natively loads
every `*.tf` in a directory, so this is picked up automatically — no change
needed to `environments/{dev,prod}/main.tf`.

The block must include:
- `source = "../../../modules/{service-name}"`
- All required input variables, wired from root variables or other modules' outputs
- Dev file uses dev values; prod file uses prod values (from `03-inputs-wave-{n}.json`)

**Dependent-variable wiring (allowed exception):**
If any previously-built service depends on this service's new outputs, add those
input variables to the dependent's `terraform/modules/{dependent}/variables.tf`
only. Do NOT touch any other file.

Show only:
```
Wired:
  terraform/environments/dev/modules/{service-name}.tf
  terraform/environments/prod/modules/{service-name}.tf
Dependent vars updated: {list or "none"}
```

## Step 6 — Lightweight sanity checks (NO terraform CLI)

Perform in-process checks on the generated files. These are cheap text checks,
not a substitute for `terraform validate` — that's `/TerraformValidator`'s job.

Checks:
1. **File presence** — all six files from Step 4 exist and are non-empty.
2. **Brace / quote balance** — count of `{` equals `}` and count of unescaped `"` is even, per file.
3. **versions.tf contract** — contains a `required_providers` block; does NOT contain `required_version` (per project standard).
4. **Tag contract** — every `resource "..." "..." {` block has a `tags = local.common_tags` line before its closing brace.
5. **No hardcoded literals** — regex-scan `main.tf` for `"us-east-1"`, `"us-west-2"`, 12-digit account IDs (`\b\d{12}\b`), and literal ARN fragments outside `data` blocks.
6. **Variable declarations** — every `var.{name}` reference in `main.tf`/`outputs.tf` has a matching `variable "{name}" {` block in `variables.tf`.

Write detailed per-check output to `agent/execution.md`.

Show in chat:
```
Sanity checks:
  ✅ files present        (6/6)
  ✅ braces/quotes        (balanced)
  ✅ versions.tf contract
  ✅ tags on resources
  ✅ no hardcoded literals
  ✅ variables declared
```

If any check fails — show the failing check + file + line, log details to
`execution.md`, and STOP. Do not update memory. User can fix and re-run
`/ServiceCodeWriter {service-name}`.

## Step 7 — Update memory (status: CODE_WRITTEN)

Update `.claude/memory/04-build-progress.json`:
- Set this service's status to `CODE_WRITTEN` in its wave entry.
- Set `iam_status` for this service to the value determined in Step 4b:
  `"CREATED"` | `"SKIPPED"` | `"NOT_REQUIRED"` | `"ERROR"`
- If `iam_status` is `"SKIPPED"`, also set `"iam_warning": true` so downstream
  commands (`/TerraformValidator`, `/DeployOrchestrator`) can surface the alert.
- Do NOT mark the wave complete — that happens only after all services reach `COMPLETE` via `/TerraformValidator`.

Update `.claude/memory/tf-state.json`:
- Set `last_command` → `"/ServiceCodeWriter"` and `last_updated` → current ISO timestamp.
- Set `current_phase` → `"DEPLOYING"`.

Write `.claude/memory/handoff.json`:
- `"next_command": "/TerraformValidator service:{service-name}"`
- `"phase": "DEPLOYING"`
