# Diagram Analyst

Reads the draw.io diagram and compares it against:
1. The generated Terraform code in `terraform/modules/`
2. The confirmed review files in `agent/review/`
3. AWS architecture best practices

Produces two types of output:
- **Drift report** — differences between diagram and generated code
- **Architecture suggestions** — improvements to the diagram/architecture itself

---

Minimum: Gate 2 confirmed (`gate2_build_plan: "CONFIRMED"` in tf-state.json).

   Run /ServiceModelerConfirm first.

## Commands

| Command | What it does |
|---------|-------------|
| `/tf-diagram-diff` | Compare diagram vs generated code — show what drifted |
| `/tf-diagram-diff {service}` | Drift check for one service only |
| `/tf-diagram-suggest` | Architecture improvement suggestions from diagram analysis |
| `/tf-diagram-suggest {service}` | Suggestions for one service only |
| `/tf-diagram-sync` | Generate a list of changes needed to bring code in sync with diagram |

## Drift Detection Logic

### Service-level drift

For each service in the diagram:
1. Check if a module exists at `terraform/modules/{service-name}/`
2. Check if the service type matches the Terraform resource type
3. Check if all connections in the diagram have corresponding dependency wiring

For each service in `terraform/modules/`:
1. Check if it still exists in the diagram (orphan detection)
2. Check if the service type still matches

### Config-level drift (when wave inputs are confirmed)

For each service with confirmed inputs (`03_inputs_wave_*.md`):
1. Check if the Terraform module uses those exact values
2. Flag any differences between the spec and the code

### Connection drift

For each arrow/edge in the diagram:
1. Check if the corresponding dependency exists in `build-plan-review.md`
2. Check if the corresponding variable/output wiring exists in the code

## Architecture Suggestion Categories

Read `references/architecture-patterns.md` for the full suggestion library.

Suggestions are generated by analysing the diagram topology:

**Reliability**
- Single points of failure (one Lambda with no DLQ, no retry)
- Missing redundancy (single-AZ RDS, no Multi-AZ)
- Missing circuit breakers or dead letter queues

**Security**
- Services with direct internet exposure that should be behind an ALB/API Gateway
- Databases in public subnets
- Missing WAF on public-facing endpoints
- Lambda functions not in VPC when accessing private resources

**Cost**
- Patterns that could use Spot/Fargate Spot
- Lambda functions with unnecessarily high memory
- Resources that could use cheaper storage tiers

**Performance**
- Missing caching layers (no ElastiCache for frequently-read data)
- Synchronous calls that could be async via SQS/SNS
- Large Lambda payloads that should use S3 pre-signed URLs

**Observability**
- Missing CloudWatch alarms
- No X-Ray tracing configured
- No centralized logging
