# Architecture Patterns & Suggestion Library

Suggestions generated by the diagram-analyst skill when reviewing architecture diagrams.

---

## Reliability Patterns

### Missing Dead Letter Queue (DLQ)
**Trigger:** Lambda function connected to SQS without a DLQ on the queue
**Suggestion:** Every SQS queue that triggers a Lambda should have a DLQ.
Failed messages after `maxReceiveCount` retries are sent to the DLQ instead of lost.
```
Add: SQS DLQ → {queue-name}-dlq
Wire: {queue-name} → redrive_policy → {queue-name}-dlq
Alert: CloudWatch alarm on DLQ depth > 0
```

### Single AZ RDS
**Trigger:** RDS instance with `multi_az = false` in prod
**Suggestion:** Enable Multi-AZ for production RDS — provides automatic failover in ~1-2 minutes.
Cost increase ~100% but critical for prod SLA.

### No Retry Logic
**Trigger:** Lambda directly invoked by API Gateway with no SQS buffer
**Suggestion:** For non-real-time operations, add SQS between API Gateway and Lambda:
```
API Gateway → SQS → Lambda
```
This adds buffering, automatic retries, and DLQ support.

### Lambda Without Concurrency Limit
**Trigger:** Lambda with `reserved_concurrent_executions = -1` in prod
**Suggestion:** Set a reserved concurrency limit to prevent runaway costs and protect downstream services from being overwhelmed.

## Security Patterns

### Database in Public Subnet
**Trigger:** RDS or ElastiCache in a public subnet (or no VPC shown)
**Suggestion:** Move database to private subnet. Only application tier should be in public/DMZ subnets.
```
Public:   API Gateway, ALB, CloudFront
Private:  Lambda, ECS, RDS, ElastiCache
```

### Direct Lambda Internet Exposure
**Trigger:** Lambda function with public URL enabled or connected directly to Route53
**Suggestion:** Put an API Gateway or ALB in front. Never expose Lambda directly.

### Missing WAF
**Trigger:** API Gateway or CloudFront without WAF mentioned
**Suggestion:** Add AWS WAF to public-facing endpoints:
- Rate limiting
- IP blocklist
- SQL injection / XSS protection
- Bot control

### Secrets in Environment Variables
**Trigger:** Lambda with `environment_variables` containing keys like `PASSWORD`, `SECRET`, `KEY`, `TOKEN`
**Suggestion:** Move secrets to Secrets Manager or SSM Parameter Store.
Reference via `aws_secretsmanager_secret_version` at runtime, not at deploy time.

### Missing VPC for Lambda Accessing Private Resources
**Trigger:** Lambda → RDS or Lambda → ElastiCache without VPC attachment
**Suggestion:** Lambda must be in the same VPC as the private resource to reach it.
Add VPC config to Lambda: subnet_ids and security_group_ids.

## Cost Optimisation Patterns

### Lambda Arm64
**Trigger:** Lambda with `architectures = ["x86_64"]`
**Suggestion:** Switch to `arm64` (Graviton2) — 20% cheaper, up to 34% faster for most workloads.
Only use x86_64 if your code has x86-specific dependencies.

### Single NAT Gateway for Multi-AZ
**Trigger:** Multiple AZs with `single_nat_gateway = false` in dev
**Suggestion:** In dev, use `single_nat_gateway = true` — saves ~$45/month per extra NAT gateway.
Keep `false` only in prod for high availability.

### RDS Oversized for Dev
**Trigger:** Dev RDS using `db.r6g.*` or `db.t3.large` or above
**Suggestion:** Use `db.t3.medium` in dev — sufficient for development, saves $100-400/month.
Reserve larger instances for prod.

### ElastiCache Oversized for Dev
**Trigger:** Dev cache using `cache.r6g.*`
**Suggestion:** Use `cache.t3.medium` in dev — saves $70-200/month vs r6g.

## Performance Patterns

### Missing Caching Layer
**Trigger:** Lambda → RDS with high call frequency, no ElastiCache in diagram
**Suggestion:** Add ElastiCache Redis between Lambda and RDS for frequently-read data.
Typical cache-hit reduces latency from ~5ms (DB) to ~0.3ms (cache).

### Synchronous Where Async Would Work
**Trigger:** API Gateway → Lambda → downstream service with no return value needed
**Suggestion:** If the client doesn't need an immediate response, make it async:
```
API Gateway → SQS → Lambda (async)
vs
API Gateway → Lambda → wait → respond (sync)
```
Async pattern handles traffic spikes better and reduces API timeout risk.

### Large Response Through Lambda
**Trigger:** Lambda connected to S3 with large file operations
**Suggestion:** Use S3 pre-signed URLs for large file transfers — bypass Lambda entirely:
```
Client → API Gateway → Lambda (generates pre-signed URL) → Client → S3 directly
```
Lambda response limit is 6MB. S3 objects can be any size.

## Observability Patterns

### No Alarms
**Trigger:** RDS, Lambda, SQS, ECS without CloudWatch alarms in diagram
**Suggestion:** Add CloudWatch alarms for:
- Lambda: error rate > 1%, duration > 80% of timeout, throttles > 0
- RDS: CPU > 80%, FreeStorageSpace < 10GB, DatabaseConnections > limit
- SQS: DLQ depth > 0, ApproximateAgeOfOldestMessage > threshold
- ECS: CPUUtilization > 85%, MemoryUtilization > 85%

### No Distributed Tracing
**Trigger:** Multi-service architecture without X-Ray in diagram
**Suggestion:** Enable X-Ray on Lambda (`tracing_config { mode = "Active" }`), 
API Gateway, and ECS tasks. Use X-Ray service map to trace requests across services.

### No Centralised Logging
**Trigger:** Multiple services without a log aggregation service shown
**Suggestion:** All Lambda and ECS CloudWatch log groups should feed into:
- CloudWatch Log Insights for ad-hoc queries
- Or OpenSearch / Datadog / Splunk for production

## Diagram-Specific Suggestions

### Unlabelled Connections
**Trigger:** Arrows in diagram with no label
**Suggestion:** Label connections with the protocol/method: HTTPS, SQL, gRPC, SQS, SNS, etc.
This makes dependency wiring explicit and avoids ambiguity during code generation.

### Missing IAM Representation
**Trigger:** No IAM roles shown in diagram
**Suggestion:** Even if IAM isn't drawn explicitly, consider adding an IAM box to show:
- Which role each Lambda/ECS uses
- Which secrets each service can access
This makes the security model visible in the architecture.

### Missing Availability Zone Layout
**Trigger:** No AZ containers in diagram
**Suggestion:** Show AZ layout explicitly — which resources are in which AZ:
- Private subnets in each AZ
- RDS primary vs standby placement
- ECS task distribution
This prevents accidentally placing all resources in one AZ.
